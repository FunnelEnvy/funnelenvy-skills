# hypothesis-generator: Experiment-History Consumption

## Background

`hypothesis-generator` produces ICE-scored experiment roadmaps from positioning, audience, competitive, performance, and (optionally) structural context. It has no input for the results of experiments already run. [score.md](../../skills/hypothesis-generator/phases/score.md) Step 7 `Sequencing` > `Layer 4: Empirical tiebreakers` item 1 (Winner Replication Priority) is written but inert: it fires "ONLY when experiment-history data exists" and names that input as a future context layer. The `Output Format` has no section for completed-experiment evidence.

In pilot use against a measurement-constrained scope, the only Quick Win the roadmap produced existed solely because a completed, statistically significant test result was hand-carried into the roadmap by the operator. That result supplied a proven mechanism and a known measurement path, which is what let one hypothesis clear the Quick Win bar that the scope's weak measurement otherwise blocked. The skill itself read none of it. On a clean re-run without the hand-carried evidence, the roadmap regresses to zero Quick Wins for that scope. The most load-bearing input was operator-supplied and did not survive a re-run.

A consumer repo now maintains a dedicated knowledge base of completed measured experiments: a medallion-model KB with a gold index rolling up every record (outcome, design, one-line insight) and per-experiment silver insight records carrying outcome, mechanism diagnosis, and a typed next-experiments backlog of rollout and replication candidates with target surfaces and priority. That KB's own contract already designates downstream strategy skills as readers of its gold layer. This change wires `hypothesis-generator` to consume such a KB through a generic, binding-resolved read contract, so completed-experiment evidence and the replication backlog reproduce on every run instead of being hand-carried.

This is a separate concern from the in-flight premise-rigor change, which is no-research and operates only on artifacts already loaded (triangulation, instrumentation, power, gated Confidence). This change adds a new optional input source. The two are complementary and share two files (`SKILL.md`, `score.md`). Coordination is soft, with no hard dependency: whichever reaches Build second rebases the shared edits. With the Step 4 replication modifier added, both changes now touch `score.md` Step 4, so they must agree on order of operations there: this change's replication lift feeds the raw Confidence and premise-rigor's gated rubric is the hard ceiling applied after soft modifiers (compatible by design). This change also edits Step 7 (sequencing) and premise-rigor adds a new `phases/validate.md`. The kb-native KB-mode foundation this change builds on is already released (hypothesis-generator v1.6.0), not a coordination partner.

## Current State

- [score.md](../../skills/hypothesis-generator/phases/score.md) Step 7 `Sequencing` > `Layer 4: Empirical tiebreakers` item 1 (Winner Replication Priority) is inert: it fires only when experiment-history data exists, which no input currently supplies, and is annotated as a future context layer. As written it is a within-tier sequencing reorder, not a Confidence-scoring modifier.
- [SKILL.md](../../skills/hypothesis-generator/SKILL.md) `Read-side Mapping` has no experiment-history row, and `Preconditions` list no such input.
- The `Output Format` has no completed-experiment-evidence section; any such content in a produced roadmap is operator-authored.
- The skill performs no cross-KB read of any kind.

## Approach

### Change Profile

- **Script-affecting: no.** No Python scripts in a skill `## Scripts` table are added, modified, or removed. The repo-level bash validator [validate-hypothesis-generator.sh](../../scripts/validate-hypothesis-generator.sh) gains presence checks (new `Output Format` section, new read contract) and a purity-grep extension for any new field names, but it is a test harness, not a registered Python script; no `_tests/` layer applies. Mirrors the sibling premise-rigor doc's classification of the same validator.
- **Performance-affecting: yes.** The change alters the skill's analytical output behavior: a new optional input source, a new completed-experiment-evidence section in the deliverable, and activation of the winner-replication sequencing path. `_evals/` does not exist in this repo, so verification is via the validator script plus a bound-KB functional regression, not the eval framework.
- **Test-eval-only: no.**

### Approach narrative

The skill gains one generic optional input: a knowledge base of completed-experiment records, discovered through the same binding the skill already uses for its optional silver inputs, never a hard-coded KB type or path.

**Discovery (generic, binding-resolved).** Add a row to the `Read-side Mapping` table in [SKILL.md](../../skills/hypothesis-generator/SKILL.md) and a soft-input bullet to `Preconditions`, both resolved from the bound repo's `Knowledge Bases` declaration exactly as the existing optional silver rows are (`silver-performance-analysis`, `silver-structural-observation`). The input degrades gracefully: absent means "no prior-experiment evidence was available," never a Confidence penalty and never a global cap, identical to the structural-observation degradation semantics already in `Preconditions` and the `phases/detect.md` graceful-degradation table. The skill names no client KB type and no path; the consumer repo's binding supplies those (Open Issue 2). Because optional silver types are not mode-resolution requirements (per the `Mode Resolution Procedure`), a missing experiment-history KB is invisible to mode resolution and the skill runs unchanged, preserving current legacy and KB behavior.

**Read contract (read-only, no dependency edge).** Read the producer KB's gold index (a rollup of completed experiments: outcome, design, one-line insight per record) plus the silver insight records it links (each carrying outcome, mechanism diagnosis, and a typed next-experiments backlog of rollout/replication candidates with target surfaces and priority). This is a read of the producer KB's gold outbound surface, the contract surface that KB's own type already designates for downstream strategy readers. It is read-only and cited by natural attribution / source pointer, with no `depends_on` graph edge into the experiment KB. That preserves both KBs' self-containment and the skill's no-research charter: a KB read is not web research, and no cross-KB dependency edge is created (Open Issue 3). Default to filtering the index to the run's `--scope`, allowing documented cross-scope reads where a win on one scope legitimately informs another (Open Issue 4).

**Output (new evidence section, pure body).** Surface completed-experiment evidence in a new `Output Format` section sourced from the insight records: outcome, mechanism, and the transferable rule, in natural language. The deliverable body stays pure per the `Deliverable Purity Constraint`: no experiment identifiers, no KB type names, no system internals, natural attribution only. The new field names introduced for this evidence are added to the `Deliverable Purity Constraint` prohibited-terms list and to the validator's purity grep so they cannot leak into the body. Whether completed-experiment signals also surface as opportunities in [detect.md](../../skills/hypothesis-generator/phases/detect.md) was deferred to Design and is resolved as INCLUDE (Requirements item 9): a new Step 1g enrichment leg, tagged `signal_source: experiment-history`, baseline 3/3/3, mirroring Step 1c/1e. It is additive, tri-state-safe, adds no phase file and no count change, and converts a prior-winner replication into a first-class detected opportunity. The evidence section in `SKILL.md` remains the load-bearing surface; the `detect.md` leg is enrichment on top of it, not a prerequisite for value.

**Scoring activation (Step 7 sequencing reorder plus a Step 4 replication modifier).** `phases/score.md` Step 7 `Sequencing` > `Layer 4: Empirical tiebreakers` item 1 (Winner Replication Priority) is currently inert: it fires "ONLY when experiment-history data exists," which no input supplies, and is annotated as a future context layer. As written, this item is a **within-tier sequencing tiebreaker** that queues a replication of a proven winner ahead of untested patterns; it is not a Confidence-scoring modifier. Activating it when the input is bound makes a completed winner whose insight carries a rollout/replication next-experiment a replication candidate that inherits the source's target surfaces and priority and sorts ahead of untested hypotheses in its tier. Decision (resolved at the Discovery gate): activation is twofold. (1) The Step 7 sequencing reorder above. (2) A new Step 4 Confidence/Ease modifier for validated-mechanism replications, because a replication clearing the Quick Win bar (Confidence >= 4 AND Ease >= 4) is a scoring outcome that only Step 4 supplies; the Step 7 reorder alone cannot produce a Quick Win. Sequencing-only was rejected: it surfaces the evidence but cannot reproduce a replication-derived Quick Win, which is the gap this change exists to close. The Step 4 modifier must coordinate with the gated Confidence rubric the sibling premise-rigor change adds: any replication Confidence lift applies to the raw Confidence and the gate remains a hard ceiling, so a replication boost never bypasses an affirmative gate failure (e.g., an uninstrumented primary metric). The sibling doc already specifies the rubric runs as a hard ceiling after the soft Step 4 modifiers, which is the order this change must respect.

### Alternatives Considered

- **Hard-code the producer KB type name and path in the skill.** Rejected. The producer KB lives in a consumer repo, not in this public skill's repo. Hard-coding a type or path would embed a client-specific identifier in a public skill and break the moment a second consumer binds a differently-named experiment KB. The skill resolves the input from the bound repo's `Knowledge Bases` declaration exactly as it does for its existing optional silver inputs (Open Issue 2).
- **Consume the producer KB's silver insight records directly as the contract surface.** Rejected as the discovery mechanism. The producer KB's contract designates its gold layer as the downstream-reader surface; reading silver directly would couple this skill to that KB's internal layer structure and violate the medallion-model boundary that lets the two KBs stay self-contained. The change reads the gold index as the entry point and follows it to the silver insights the index links, rather than globbing silver directly (Open Issue 3).
